# Archival benchmark

This experiment asks whether content-defined deduplication earns its metadata
overhead when retaining evolving agent traces. It compares Nenia with independently
compressed snapshots and one solid Zstd stream. All candidates use Zstd level 9,
checksums, a declared input size, and a maximum 8 MiB window. This is a synthetic
local batch experiment, not a forecast of compression on a user's private traces.

## Experiment specified before collection

The primary metric is retained file bytes for a complete, restorable history.
The decision rule is to retain chunk deduplication if it saves at least 20% against
independent Zstd snapshots on both append history and shared-prefix forks, while
adding less than 5% archive overhead on the incompressible control. This rule
applies to packs plus manifests, before the separately reported disposable catalog.
Every snapshot must restore byte-for-byte. Ingestion elapsed time is diagnostic;
three short trials cannot establish sustained throughput or a service capacity.
No compressor tuning will be performed after looking at this matrix.

The deterministic generator in [examples/benchmark.rs](../examples/benchmark.rs)
uses seed `4e454e4941323032`. Its JSONL records mix user requests, explanations,
code diffs, tool logs, and test results. Event IDs, request identifiers, digests,
timestamps, paths, counters, and numeric arguments vary. Text templates remain
synthetic and intentionally do not imply a representative distribution of real
agent output. A random binary control exercises the opposite extreme.

| Workload | Shape at scale 1 | What it measures |
| --- | --- | --- |
| Independent | 16 independently generated sessions, about 512 KiB each | Cross-file compression with little exact chunk reuse |
| Append history | 6 sessions, 6 versions each; 512 KiB initially and about 128 KiB appended each round | Storage cost of retaining earlier snapshots |
| Shared-prefix forks | 12 sessions sharing about 1 MiB, each with about 256 KiB unique continuation | Exact prefix reuse across files |
| Entropy | 4 independently generated 2 MiB binary files | Incompressible overhead and lossless arbitrary-byte handling |

JSONL sizes are rounded upward to complete records. `workloads.json` records the
exact size and BLAKE3 hash of every generated snapshot.

## Measurement boundary and controls

Each candidate gets a fresh archive directory. Source fixtures are generated and
written immediately before ingestion, outside the timer; they are consequently
warm in the operating system cache. Input reads, hashing, compression, manifest
serialization, immutable file publication, file synchronization, and directory
synchronization are timed. Nenia additionally times vault initialization, source
metadata extraction, catalog transactions, checkpoints, and catalog close. SQLite
uses WAL mode with `synchronous=FULL`. Baselines use the same immutable publication
helper and compressed mapping manifests. The solid baseline flushes one final
payload object, while the other candidates publish smaller independent objects.

Preparation and inter-round source updates are excluded. Timings accumulate those
completed work intervals using `Instant`, a monotonic clock. Correctness checks,
storage accounting, optional content indexing, logging, and cleanup are excluded
from ingestion time. Index time includes content extraction, FTS updates,
checkpoints, and database close, but excludes reopening the vault. The index cap
is 8 MiB per snapshot; these fixtures are smaller than that cap.

After every measured candidate, every stored snapshot is decoded and compared
directly with its generated bytes. The run aborts on any failed write, unexpected
snapshot count, or restore mismatch; an error record is retained. There are no
retries and no excluded successful trials. All files are counted after closing
SQLite, so transient shared-memory and WAL files do not inflate catalog size.
Sizes are file lengths, not filesystem block allocation or object-store billing.
Nenia total bytes also include its small configuration file.

Three independent trials are planned, with candidate order rotated each trial:
per-file/solid/Nenia, solid/Nenia/per-file, Nenia/per-file/solid. Fresh archive state
is controlled; cold storage is not. A separate small correctness smoke run precedes
measurement. No steady-state warmup or storage-cache flush is claimed. The process
shares a development host; competing work, underlying virtual storage hardware,
power state, and thermal state are uncontrolled and disclosed in the environment
manifest. These limitations make small timing differences unresolved.

The baseline mapping manifests preserve file boundaries and names, and permit
full restoration. They do not implement Nenia's query catalog, immutable snapshot
history interface, independently recoverable manifests, or additive remote sync.
Solid Zstd may require reading the whole stream to reach one snapshot. These are
storage-layout comparisons with equivalent byte preservation, not identical
products or identical random-access costs.

## Reproduce

From the repository root, with Rust available on `PATH`:

```sh
cargo build --release --example benchmark
target/release/examples/benchmark --output /tmp/nenia-benchmark-smoke --trials 1 --scale 0.0625
target/release/examples/benchmark --output /tmp/nenia-benchmark-full --trials 3
```

Output directories must not exist, so earlier evidence cannot be silently replaced.
Optional `--case entropy`, `--scale`, `--level`, and `--trials` select another
experiment; changed configurations must be reported separately. Temporary archive
artifacts are removed after their samples; generator code, snapshot hashes, raw
results, and environment details remain sufficient to reproduce the work.

Each output directory contains `environment.json`, `workloads.json`,
`samples.jsonl`, and `summary.json`. Summary rows contain median, minimum, and
maximum elapsed seconds across independent trials and byte-size ranges. Every raw
row records order, timestamps, input size, completed snapshots, restored snapshots,
errors, archive components, total local bytes, and optional index overhead. Median
throughput is input MiB divided by median elapsed seconds; it is archival input
throughput, including bytes deduplicated away, not physical disk write throughput.
